# 新网格模块自动化测试系统开发指南

## 一、任务背景

本任务面向新网格模块的自动化测试系统建设，目标不是简单补几条测试，而是形成一套可持续扩展、可回归、可复核的测试机制。

你们需要围绕四个核心工作展开：

1. 调研成熟项目在自动化测试系统上的常见做法，提炼可直接复用的设计原则。
2. 针对当前新网格模块，生成适当的单元测试和集成测试，可结合 AI 辅助完成测试用例设计与补全。
3. 设计自动化测试系统，并通过真实运行验证其可用性、稳定性和可维护性。
4. 发现并上报新网格模块中的 Bug，以及接口、分层、命名、职责边界等设计不合理之处。

这个任务的重点是“测试系统”本身，而不是把新网格模块一次性测完整。

建议分支：`feature/mesh-02-test-system`，任务完成后PR合并回 `feature/mesh`；
建议 task：在 `kb/developments/new_mesh_module/mesh_02_test_system` 目录下完成，若有必要可以通过子目录的方式添加子任务。

注：测试进入 tests 目录，而非 test。

## 二、任务边界

本任务明确包含：

- 调研自动化测试系统的成熟实践，包括测试分层、夹具组织、参数化、回归策略、CI 触发方式、报告输出等。
- 为当前新网格模块设计并生成单元测试、集成测试，以及必要的回归测试样例。
- 设计自动化执行流程，确保测试可以稳定重复运行，并能为后续扩展留下接口。
- 对测试过程中暴露出的 Bug 和设计缺陷进行记录、归类和上报。

本任务明确不包含：

- 任何其它 FEALPy 模块的测试文件。
- 新网格模块的完整测试覆盖。
- 为了追求覆盖率而无边界扩张到无关代码路径。

如果某个测试点会自然触及公共基础设施，只允许做到“验证新网格模块的使用链路”，不允许把任务扩展成跨模块全面测试。

## 三、建议的调研方向

调研时建议重点关注以下问题：

1. 成熟项目如何划分测试层级，哪些内容放单元测试，哪些内容放集成测试，哪些内容放回归测试。
2. 测试夹具、测试数据、临时文件、随机种子如何管理，才能保证可重复运行。
3. 如何用参数化测试压缩重复样板，同时保持失败定位清晰。
4. 如何把 AI 辅助生成的测试收敛为可审查、可维护的资产，而不是一次性脚本。
5. 如何在 CI 中组织测试选择、失败报告和最小可复现信息。

调研输出不要停留在“别人用了什么工具”，而要落到“我们为什么照搬、照搬哪些、哪些不适合 FEALPy 新网格模块”。

## 四、测试系统设计建议

建议把测试系统按下面的思路组织：

### 1. 测试分层

- 单元测试：针对纯计算逻辑、局部数据结构、边界条件判断、输入校验等小粒度逻辑。
- 集成测试：针对新网格模块的构造、查询、转换、关联关系、端到端调用链等。
- 回归测试：针对历史缺陷、已修复 Bug、设计缺口暴露出的固定场景。

### 2. 资产分层

- 测试代码：只覆盖新网格模块相关路径。
- 测试数据：尽量小而稳定，便于版本管理。
- 运行脚本：统一入口，避免测试散落在临时 notebook 或手工命令里。
- 结果记录：保留失败样例、异常栈、关键中间量和判定依据。

### 3. 设计原则

- 可重复：同一输入应得到同一输出，避免依赖隐式环境状态。
- 可定位：失败时能快速指出是哪一层出错，而不是只给出一个模糊断言失败。
- 可扩展：后续新增网格类型时，测试结构不需要重写。
- 可收口：测试系统要能说明当前已经覆盖了哪些核心能力，哪些仍是空白。

## 五、建议的执行步骤

### A：调研与基线梳理

- 先阅读成熟项目的测试组织方式，提炼可迁移的模式。
- 再梳理当前新网格模块的公开 API、核心数据流和高风险接口。
- 给出一份最小测试矩阵，明确每个测试点的目标、输入、预期、断言方式和归类。

### B：生成测试用例

- 针对新网格模块中最容易出错的部分优先写测试。
- 单元测试优先覆盖局部逻辑、异常输入和边界条件。
- 集成测试优先覆盖对象构造、关系查询、数据流通路和典型使用链路。
- 可用 AI 辅助生成初稿，但必须人工复核断言是否真正对应模块语义。

### C：设计自动化测试系统

- 统一测试入口，建议能通过单一命令或统一任务触发。
- 明确测试目录、命名规范、夹具组织和测试数据存放位置。
- 为失败输出保留足够上下文，便于快速复现和修复。
- 若有 CI 环境，优先让测试系统适配 CI，而不是只适配本地手工运行。

### D：验证与回归

- 运行测试系统并记录结果。
- 修复能修复的 Bug，保留暂时无法修复但已经定位的问题。
- 将已确认的问题写入问题单，形成可追踪记录。
- 对自动化测试系统自身做一次最小回归，确认新增测试不会破坏已有稳定场景。

## 六、Bug 与设计问题上报要求

测试过程中发现的问题，至少分成三类记录：

- 代码 Bug：逻辑错误、边界条件错误、异常处理缺失、结果不稳定。
- 接口问题：参数语义不清、返回值不一致、调用链过深、难以测试。
- 设计问题：职责混杂、分层不清、测试依赖过重、模块耦合过高。

每个问题都应尽量包含：

- 复现步骤
- 触发输入或场景
- 预期行为
- 实际行为
- 影响范围
- 是否适合立刻修复

## 七、输出要求

每位参与者至少要输出以下几类可追溯资产中的一项或多项：

- 自动化测试系统设计说明
- 新网格模块示例单元测试文件
- 新网格模块示例集成测试文件
- 测试运行脚本或统一入口
- Bug / 设计问题清单
- 测试验证记录或回归结果

最终收口时，每位参与者都应能回答：

- 新网格模块应该按什么层级做测试
- 哪些场景最值得自动化
- 哪些问题是 Bug，哪些是设计缺陷
- 当前测试系统是否已经能稳定支持后续迭代
- 本次产物是否只覆盖了新网格模块，而没有越界到其它 FEALPy 模块
