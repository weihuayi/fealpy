# FEALPy | Design | 计算软件互操作架构设计

- **版本**：v0.2
- **状态**：草案
- **入库位置**：`kb/design/interop/interop_architecture.md`
- **启用条件**：当设计、实现、评审或演化 FEALPy 与外部计算软件、计算数据标准或模型交换协议之间的互操作能力，或判断相关能力与 FEALPy 核心领域模块的边界时，本文件应作为架构设计依据
- **适用范围**：FEALPy 计算软件互操作模块，以及其与 FEALPy 核心领域模块之间的对象边界、转换关系和依赖关系

## 一、文档定位与设计目标

### 1.1 文档定位

本文档定义 FEALPy **计算软件互操作（Computational Software Interoperability）**的整体架构、对象边界、核心职责分层、依赖方向、语义保真要求和增量演进原则，用于指导 `fealpy.interop` 的持续设计、实现、评审与重构。

本文档是一份持续接受实践检验的架构设计基线，不是一次性终态规格。它不预先规定未来所有代码对象、公共接口和目录结构，而是为后续局部设计和增量实现提供稳定的判断坐标。

本文档重点回答：

- 什么问题属于 `fealpy.interop`；
- 什么问题仍属于 Mesh、FEM、Material 等 FEALPy 核心领域；
- 外部计算系统的语义如何在不污染 FEALPy 核心领域模型的前提下进入 FEALPy；
- 外部数据经过哪些职责边界完成语义转换；
- 不同外部系统如何逐步接入而不在 `interop` 内形成与 FEALPy 核心领域竞争的公共 CAE 本体；
- 如何判断一次互操作的支持范围、语义损失和计算可信程度；
- 如何通过真实需求和验证与确认持续修订架构。

### 1.2 设计目标

`fealpy.interop` 服务以下目标：

1. 建立 FEALPy 与外部计算生态之间稳定、清晰且可扩展的互操作边界；
2. 保持 FEALPy 自身领域模型的主位，避免外部软件对象体系反向塑造核心模块；
3. 支持具有不同语义结构、载体形式和版本体系的外部计算系统逐步接入；
4. 分离外部物理表示、外部模型语义和 FEALPy 领域语义；
5. 使支持范围、映射损失和不支持情况能够被显式识别、诊断和验证；
6. 支持第三方库作为可选后端、参考实现或验证工具，而不将第三方数据模型变成 FEALPy 核心依赖；
7. 采用真实需求驱动的增量开发方式，使公共抽象随实践逐步形成和修正。

### 1.3 非目标

本文档当前不：

- 构建覆盖不同计算软件的通用 CAE 中间模型；
- 定义 Abaqus、Nastran 或其它外部系统的完整数据模型；
- 一次性规定所有未来互操作对象、类和公共 API；
- 要求所有外部互操作实现具有完全相同的内部结构；
- 要求所有逻辑职责独立成为 Python 类、文件或包；
- 保证任意两个计算系统之间可以无损转换；
- 定义具体 Abaqus 关键词（Keyword）、Nastran 卡片（Card）或其它格式记录的解析细节；
- 替代具体互操作开发任务的需求、实施步骤、测试计划和执行流程；
- 以当前 Abaqus 或 Nastran 需求冻结 FEALPy 未来的领域模型。

### 1.4 当前成熟度

v0.2 是基于 FEALPy 新 Mesh 架构、当前 Abaqus/Nastran 实际需求及相关外部实践研究形成的初始架构设计。

本文档中的对象主位、核心依赖方向、语义保真和增量演进原则具有较高的预期稳定性；具体外部表示、适配接口、公共 API 和物理代码结构仍需通过实际互操作场景持续检验。

## 二、背景问题与设计驱动力

### 2.1 从文件读写到计算模型互操作

FEALPy 与外部数据的交换至少可以区分三个层次：

1. **序列化（Serialization）**：解决数据如何被存储和恢复；
2. **领域输入输出（Domain I/O）**：解决某一 FEALPy 领域对象如何与外部数据格式交换；
3. 计算软件互操作：解决具有独立计算语义的外部模型、结果或其它计算对象如何映射到 FEALPy 的一个或多个领域对象。

如果外部数据主要由点坐标、实体连接关系和实体附加数据构成，并直接映射为 FEALPy Mesh，则问题主要属于 Mesh 的领域输入输出。

当外部数据同时表达材料、属性、具名集合、约束、载荷、坐标系、分析设置或结果等对象时，问题已经超过单一 Mesh I/O。

此时可以把互操作抽象为：

$$
M_{\mathrm{external}}
\overset{\Phi}{\longleftrightarrow}
M_{\mathrm{FEALPy}},
$$

其中需要重点设计和检验的是语义映射 $\Phi$，而不仅是外部文件是否能够被解析。

### 2.2 核心矛盾

外部计算软件、计算数据标准和模型交换协议拥有自己的对象体系、编号体系、引用关系、版本规则和计算语义。

FEALPy 需要理解并消费这些语义，但不能因此让某个外部系统的对象体系成为 FEALPy 自身的领域模型。

因此，互操作设计需要同时满足两个要求：

> 对外部语义保持足够忠实，同时保持 FEALPy 内部领域模型的独立性。

如果在读取外部数据时直接修改 FEALPy Mesh、Material 或 FEM 对象，外部格式解析、外部模型一致性和 FEALPy 语义映射容易混为一体。

如果为了统一不同外部系统而先建立一套新的公共 CAE 中间模型，又容易在 `interop` 中复制 FEALPy 已有或未来应由核心领域维护的对象。

`fealpy.interop` 的主要架构职责，就是在这两个风险之间建立稳定边界。

### 2.3 现实驱动力

当前最直接的互操作需求来自 Abaqus 和 Nastran。

未来还可能出现：

- 其它有限元模型与结果数据库；
- CFD 等计算数据标准；
- 模型交换和协同仿真协议；
- 矩阵及求解结果交换；
- 第三方计算软件 API。

这些对象可以持续检验本文架构，但任何单一外部系统都不应成为 `interop` 本体的定义来源。

## 三、架构边界与核心原则

### 3.1 FEALPy 核心领域保持主位

FEALPy 的 Mesh、Material、FEM 以及其它核心领域语义，应由对应领域模块定义。

`interop` 可以读取、构造、引用和转换这些领域对象，但不重新定义它们。

外部软件中的某个对象能否映射为 FEALPy 对象，应依据该对象的计算语义和 FEALPy 已有领域定义判断，而不是依据外部名称建立同名 FEALPy 类型。

### 3.2 核心领域不反向依赖 Interop

核心依赖方向应保持为：

```text
External System
      │
      ▼
fealpy.interop
      │
      ├────► fealpy.mesh
      ├────► fealpy.fem
      ├────► fealpy.material
      └────► other FEALPy domains
```

即：

$$
\text{Core Domain}\not\rightarrow\text{Interop}.
$$

外部软件名称、格式、版本和专属对象不得成为 FEALPy 核心领域模块成立的前提。

### 3.3 Interop 不建立竞争性公共 CAE 本体

本文不排除 FEALPy 未来形成更加完整的有限元离散模型或其它跨领域模型。

本文限制的是另一种情况：

> `interop` 不定义一套独立于 FEALPy 核心领域、供不同外部系统先统一映射后再进入 FEALPy 的第二套公共 CAE 本体。

不推荐形成：

```text
Abaqus ───┐
Nastran ──┼──► Interop Universal Model ───► FEALPy Core
Other ────┘
```

不同外部系统真正稳定共享的计算语义，应进入 FEALPy 对应核心领域，由核心领域承担主定义和长期维护责任。

### 3.4 外部语义不由文件后缀定义

文件扩展名、文本布局和底层存储格式本身不足以定义一个互操作对象。

同一外部语义可能通过多个文件、数据库或 API 表达，同一个文件扩展名也可能服务于不同语义体系。

因此，应先识别外部语义边界，再识别其实际载体和编码方式。

### 3.5 语义保真优先于转换便利

“能够读取”不等于“能够正确互操作”。

当外部语义无法被 FEALPy 完整表达时，必须能够区分支持范围和映射损失，不得因为程序能够继续执行而静默忽略具有计算意义的信息。

### 3.6 逻辑职责与物理代码结构分离

本文识别的：

```text
Source
Codec
External Representation
Semantic Resolution
Adapter
```

首先表示逻辑职责，不表示必须存在同名 Python 类、文件或目录。

简单实现可以将多个职责物理放在同一个文件中，但其逻辑边界仍应可识别。

代码规模和真实复杂度增长后，再决定是否进一步拆分物理承载。

### 3.7 真实需求驱动公共抽象

公共抽象应来自：

- 多个真实场景已经暴露出的稳定共性；
- 或由明确架构不变量直接要求的共同机制。

不得仅根据“未来可能需要”预先建立大量基类、工厂、注册表、统一模型或公共中间层。

## 四、与 FEALPy 核心领域的关系

### 4.1 总体关系

`interop` 位于外部计算生态与 FEALPy 核心领域之间：

```text
External Computational Ecosystem
               │
               ▼
        fealpy.interop
               │
        ┌──────┼──────┐
        ▼      ▼      ▼
       Mesh    FEM   Material
               │
               ▼
        Other FEALPy Domains
```

`interop` 负责跨边界语义转换，FEALPy 核心领域负责定义转换结果本身是什么。

### 4.2 与 Mesh 的边界

Mesh 的实体、拓扑、几何和实体集合属于 `fealpy.mesh` 的主维护边界。

本文依赖 Mesh 提供原生的**实体集合（EntitySet）**能力，但不在 `interop` 中重新定义 EntitySet。

对于某个 `EntitySector` 的实体域 $E_s$，EntitySet $S$ 的基本语义为：

$$
S\subseteq E_s.
$$

当前已经形成的设计方向是：

```text
MeshBlock
└── EntitySector
    └── EntitySet
```

即 EntitySet 严格归属于一个 EntitySector，EntitySector 严格归属于一个 MeshBlock。

这一对象关系应同步进入 Mesh 设计资产，并由 Mesh 侧继续维护具体存储方式和 API。当前 `MeshBlock`、`EntitySector` 已有实现基础；EntitySet 仍属于需要同步进入 Mesh 设计和实现的前置能力。

外部系统中的 NSET、ELSET、physical group 等对象是否以及如何映射为 EntitySet，由具体适配器依据其语义判断。

### 4.3 与领域输入输出的边界

如果一个外部表示主要是某一 FEALPy 领域对象的序列化或数据交换，例如：

$$
\text{External Mesh Format}
\longleftrightarrow
\text{FEALPy Mesh},
$$

且不需要建立独立的外部计算语义模型，则优先由该领域自己的 I/O 能力承载。

当外部体系具有独立对象语义、引用关系、版本或方言规则，需要真正的语义转换时，则应评估由 `fealpy.interop` 承载。

跨越多个 FEALPy 领域是进入 `interop` 的重要信号，但不是机械判据。即使当前只消费某个外部体系的一部分数据，只要其完整语义具有独立维护价值，也可能适合由 `interop` 作为主维护位置。

### 4.4 混合场景与唯一主维护位置

一个完整外部体系由 `interop` 维护时，某个 FEALPy 核心领域仍可以根据实际使用需要提供浅层便利入口。

此时应保持：

```text
Domain Convenience API
        │
        ▼
Interop Authoritative Implementation
```

而不是在两个模块中分别维护解析和转换实现。

同一种可演化外部语义必须具有可判定的唯一主维护位置。

## 五、外部互操作对象关系

### 5.1 外部语义域

**外部语义域（External Semantic Domain）**是具有相对独立对象体系、语义规则、版本或方言体系以及兼容规则的外部计算语义边界。

外部语义域可以来源于：

- 具体计算软件；
- 软件或格式家族；
- 行业或社区数据标准；
- 模型交换协议。

候选例子包括 Abaqus、Nastran、CGNS 和 FMI。

这些来源类型用于解释语义由谁定义，不要求在 `interop` 下再建立 `software/`、`standard/`、`protocol/` 等额外分类层。

### 5.2 互操作载体

**互操作载体（Interoperability Artifact）**是某一外部语义域用于实际承载模型、结果、矩阵或其它计算信息的文件、数据库、容器或 API。

例如，一个外部语义域可以拥有多个互操作载体：

```text
Abaqus
├── INP
└── ODB

Nastran
├── BDF
├── OP2
└── OP4
```

外部语义域回答“这些数据按谁的语义解释”，互操作载体回答“这些语义通过什么对象被交换”。

### 5.3 版本与方言

同一外部语义域下可能存在多个版本或**方言（Dialect）**。

因此，互操作对象的身份通常至少需要考虑：

$$
\text{Interop Identity}
=
\text{Semantic Domain}
+
\text{Artifact}
+
\text{Version/Dialect}.
$$

实际实现不要求立即将该关系物化为统一的 `InteropIdentity` 类。

### 5.4 语义覆盖

**语义覆盖（Semantic Coverage）**描述某个互操作载体包含或能够提供哪些类型的计算语义，例如：

- Mesh；
- Model；
- Results；
- Matrices；
- Execution。

一个互操作载体可以同时覆盖多个语义类别。

因此，语义覆盖是描述维度，不是物理目录归属规则。

例如，一个结果数据库可以同时包含 Mesh、元数据和结果，不应因此为同一载体建立多套解析实现。

## 六、纵向职责分层

一个典型互操作数据流可以表示为：

$$
\text{Source}
\rightarrow
\text{Codec}
\rightarrow
\text{External Representation}
\rightarrow
[\text{Semantic Resolution}]
\rightarrow
\text{Adapter}
\rightarrow
\text{FEALPy Domain}.
$$

方括号表示对应职责并非所有互操作载体都必须独立具有。

### 6.1 数据源与数据目标

**数据源/数据目标（Source/Target）**负责说明数据从哪里获得以及写向哪里。

数据源可能包括：

- 文件路径；
- 文件流；
- 多文件组合；
- include 引用关系；
- 外部 Python API；
- 其它数据访问接口。

这一职责不负责定义外部计算语义。

v0.2 不要求立即建立统一 `DataSource` 类。

### 6.2 编解码器

**编解码器（Codec）**负责外部物理表示与可解释外部表示之间的转换。

其典型职责包括：

- 关键词或卡片解析；
- continuation line；
- fixed/free field；
- binary record；
- encoding；
- serialization。

在逻辑职责上，Codec 不应依赖 FEALPy Mesh、Material、FEM 等核心领域对象。

### 6.3 外部表示

**外部表示（External Representation）**是外部语义在 FEALPy 互操作边界内部的可操作表示。

它忠实于特定外部语义域，不追求跨外部系统统一。

根据互操作载体特征，外部表示可以采用不同形态，例如：

- 完整物化的对象模型；
- **延迟加载视图（Lazy View）**；
- 数据提供器（Provider）；
- record stream；
- 其它满足当前语义范围的局部表示。

对于模型型载体，形成较完整的外部模型表示通常具有实际价值。

对于大型结果数据库，则可能更适合采用延迟访问方式，而不是一次性完整物化。

本文不预设统一 `BaseExternalModel`。

### 6.4 语义解析

**语义解析（Semantic Resolution）**负责建立和检查外部表示内部的语义关系，例如：

- 外部编号交叉引用；
- 名称引用；
- include 引用解析；
- 默认值处理；
- 版本或方言归一化；
- 引用完整性检查；
- 外部模型内部一致性检查。

这一职责首先回答：

> 外部对象自身能否被一致解释？

而不是：

> FEALPy 是否能够支持这个外部对象？

对于没有复杂引用关系的互操作载体，语义解析不必独立物化。

### 6.5 适配器

**适配器（Adapter）**负责外部表示与 FEALPy 核心领域之间的语义映射。

其逻辑关系为：

$$
M_{\mathrm{external}}
\longleftrightarrow
M_{\mathrm{FEALPy}}.
$$

典型职责包括：

- 外部网格实体与 FEALPy EntitySector 的映射；
- 外部具名实体集合与 EntitySet 的映射；
- 外部材料和有限元模型语义与 FEALPy 对应领域对象的映射；
- 外部结果与 FEALPy 对应领域对象的映射；
- 外部编号与 FEALPy 内部索引之间的关系维护；
- 支持范围和语义损失判断。

在逻辑职责上，格式解码与领域适配应保持可区分。简单实现可以将二者物理放在同一文件中，但不得把外部格式判断散入 FEALPy 核心领域逻辑。

### 6.6 FEALPy 核心领域

数据完成适配并进入 FEALPy 核心领域后，`interop` 的主要转换职责结束。

后续有限元空间构造、积分、组装、求解和领域内部后处理属于 FEALPy 自身计算链，不属于 `interop` 的主职责。

## 七、模块组织与公共接口原则

### 7.1 一级组织单位

`fealpy.interop` 的一级物理组织优先围绕外部语义域形成。

当前真实需求下，可以从：

```text
fealpy/
└── interop/
    ├── abaqus/
    ├── nastran/
    └── ...
```

开始。

不要求额外建立：

```text
software/
standards/
protocols/
```

等分类层。

### 7.2 互操作载体按复杂度物化

互操作载体是外部语义域内部自然的组织维度，但不要求从第一版就全部成为独立 Python 包。

例如，简单阶段可以采用：

```text
abaqus/
├── inp.py
├── model.py
└── adapter.py
```

当解析、写出、外部表示或适配逻辑的复杂度真实增长后，再进一步拆分为目录或多个模块。

职责边界应先于目录层级稳定。

### 7.3 公共互操作基础设施按实际共性形成

v0.2 不预设必须存在 `_core` 目录。

当多个外部语义域或互操作载体已经暴露出稳定共享机制时，可以进一步评估公共承载位置，例如：

- 映射诊断；
- 外部编号映射；
- provider 注册；
- 公共互操作元数据。

公共互操作层不得承载 Element、Material、Section、Surface、Load、Constraint 等领域对象。

一个候选对象只有在脱离具体外部语义域和具体 FEALPy 领域语义后仍具有独立互操作意义时，才适合进入公共互操作基础设施。

### 7.4 公共 API

**公共 API（Public API）**应尽量保持浅层、稳定，并与内部物理目录结构解耦。

例如更倾向：

```python
from fealpy.interop.abaqus import read_inp
```

而不是要求用户依赖深层内部路径。

内部模块可以随实际复杂度继续拆分，只要不必要地破坏公共调用方式。

v0.2 暂不定义统一的：

```python
fealpy.interop.read(...)
```

因为不同互操作载体最终对应的 FEALPy 领域对象尚未形成足够稳定的统一返回语义。

## 八、语义保真与验证与确认

### 8.1 验证与确认范围

互操作正确性不能只通过“解析没有报错”判断。

本文采用**验证与确认（Verification and Validation, V&V）**视角，将互操作质量至少区分为以下层次。

### 8.2 外部表示验证

第一层关注：

$$
\text{Artifact}
\rightarrow
\text{External Representation}.
$$

需要检验：

- 原始记录是否被正确解析；
- 外部编号和数据值是否完整；
- 必要的版本、方言和属性信息是否保留；
- 外部引用关系是否能够被一致解释。

### 8.3 语义映射验证

第二层关注：

$$
\text{External Representation}
\rightarrow
\text{FEALPy Domain}.
$$

需要检验转换后的 FEALPy 对象是否保持目标计算所需要的外部语义。

这种等价通常不是 Python 对象结构完全相同，而是在明确适用范围内具有所需语义等价性：

$$
M_{\mathrm{external}}
\simeq
M_{\mathrm{FEALPy}}.
$$

### 8.4 计算层验证与确认

当转换结果进入真实计算链时，应根据预期用途进一步检验：

$$
M_{\mathrm{external}}
\rightarrow
M_{\mathrm{FEALPy}}
\rightarrow
\text{Computation}.
$$

根据问题类型，可以比较：

- 组装矩阵；
- 载荷向量；
- 约束后的离散系统；
- 特征值；
- 位移、应力或其它物理量；
- 其它能够反映目标计算语义的结果。

并非所有互操作能力都必须执行完整求解级 V&V，但只要转换结果用于计算，就不能仅以“FEALPy 对象成功构造”作为最终正确性依据。

### 8.5 支持覆盖

**支持覆盖（Support Coverage）**回答：

> 当前实现覆盖外部对象语义的范围有多大？

至少应能够区分：

- **支持（Supported）**；
- **部分支持（Partially Supported）**；
- **不支持（Unsupported）**。

部分支持必须能够指出未被当前实现覆盖的语义范围。

### 8.6 映射保真度

**映射保真度（Mapping Fidelity）**回答：

> 已经执行的语义映射是否发生了信息或计算意义上的损失？

至少应能够区分：

- **精确映射（Exact）**；
- **有损映射（Lossy）**。

支持覆盖与映射保真度是两个不同维度。

例如，一个对象可以是“部分支持 + 精确映射”，表示只覆盖其中部分语义，但已覆盖部分能够被准确转换；也可以是“支持 + 有损映射”，表示整体可以转换，但某些语义只能降级表达。

v0.2 不要求立即将这两个维度实现为 enum 或统一报告类，但不允许通过静默忽略信息伪装完整成功。

### 8.7 往返转换

**往返转换（Round-trip Conversion）**：

$$
\text{External}
\rightarrow
\text{FEALPy}
\rightarrow
\text{External}
$$

不是所有互操作对象的强制目标。

只有在模型编辑、修改后回写或跨系统交换等真实场景需要时，才应将往返保真作为专项能力和验证目标。

### 8.8 第三方库

meshio、pyNastran、VTK 相关库等第三方能力可以用于：

- 可选解析后端；
- 参考实现；
- 差分测试；
- 格式覆盖补充；
- 验证脚手架。

第三方库的数据对象不得成为 FEALPy 核心领域的稳定数据模型。

第三方依赖应停留在 `interop` 或相应领域 I/O 的边界以内。

## 九、增量实现与架构演进

### 9.1 纵向切片

`interop` 优先采用**纵向切片（Vertical Slice）**推进开发。

每个增量围绕一个真实使用场景形成完整闭环：

$$
\text{Real Use Case}
\rightarrow
\text{Minimal Semantic Scope}
\rightarrow
\text{End-to-End Implementation}
\rightarrow
\text{V\&V}
\rightarrow
\text{Architecture Feedback}.
$$

每次只实现完成当前场景所需的最小语义范围，不要求先实现某个外部语义域的全部对象。

### 9.2 演进闭环

每个互操作增量原则上经历：

```text
真实需求
   │
   ▼
最小语义范围
   │
   ▼
外部表示
   │
   ▼
适配
   │
   ▼
FEALPy 核心领域
   │
   ▼
真实 V&V
   │
   ▼
摩擦与反例
   │
   ▼
局部修正或抽象升级
```

架构设计应接受这一闭环产生的新证据。

如果真实实现反证已有设计，应优先修订设计，而不是通过持续增加局部兼容代码维护错误抽象。

### 9.3 公共抽象的形成条件

一个实现细节进入公共 API 或跨外部语义域公共抽象前，应至少满足以下之一：

- 多个真实外部语义域或互操作载体已经出现相同且稳定的需求；
- 明确架构不变量直接要求共享；
- 不进行抽象已经产生明显重复、行为漂移或可靠性风险。

单一外部系统当前实现中的局部便利，不构成提升为公共抽象的充分理由。

### 9.4 外部表示的演化

外部表示不要求一次设计完整。

对于模型型互操作载体，可以从当前纵向切片所需的最小语义对象开始，再随真实场景逐步扩展：

- 新对象类型；
- 新引用关系；
- 新版本或方言；
- 延迟加载；
- 往返转换所需信息。

不得仅以未来可能支持为理由，一次性重建完整外部软件对象模型。

### 9.5 架构重新审查的触发条件

出现以下情况时，应重新检查本文设计：

- 新外部语义域无法自然进入现有边界；
- 领域输入输出与 `interop` 的边界出现稳定反例；
- 多个外部系统暴露出当前尚未抽象的真正公共机制；
- 现有公共抽象实际只服务于单一外部系统；
- 外部表示与 FEALPy 核心领域出现职责混淆；
- FEALPy 核心领域开始反向依赖 `interop`；
- 公共 API 需要持续进行破坏性调整；
- 转换出现无法显式诊断的语义损失；
- 新模型、数据或计算结果反证现有映射假设。

## 十、架构验证与开放问题

### 10.1 首轮架构验证

当前计划以 Abaqus INP 作为首个完整纵向切片候选，用于检验：

- 外部语义域与互操作载体的组织方式；
- 外部表示是否具有实际必要性；
- 外部编号和引用解析能否与领域适配保持清晰边界；
- Mesh、EntitySet 和其它 FEALPy 核心领域是否能够自然承载转换结果；
- 支持覆盖和映射保真度是否能够被显式表达；
- 当前物理目录和公共 API 是否需要调整。

具体支持范围、实施步骤、代码修改位置和验收标准应进入独立开发任务，不由本文定义。

### 10.2 后续架构压力测试

Nastran 可作为后续重要压力测试来源。

其多个互操作载体及不同方言可以进一步检验：

- 同一外部语义域下多个互操作载体的组织方式；
- 不同语义覆盖是否能够保持正交；
- 完整物化模型与延迟结果访问是否可以共享同一纵向职责原则；
- 版本和方言是否需要进一步物化为公共互操作机制。

其它外部软件、标准和协议应在真实需求出现后进入同样的架构检验过程。

### 10.3 当前开放问题

以下问题当前缺少足够实践证据，v0.2 不提前冻结：

- EntitySet 第一版最终采用简单映射还是独立 class；
- 是否以及何时需要统一转换诊断报告对象；
- 是否需要公共互操作注册机制；
- 外部语义域是否需要物化为 Python 对象；
- 是否需要统一数据源抽象；
- Abaqus 外部表示的具体对象粒度；
- FEALPy 更完整的有限元模型对象如何组织；
- 结果、矩阵等领域语义最终由哪些 FEALPy 核心对象承载；
- 是否需要统一顶层 `fealpy.interop.read()`；
- 公共互操作基础设施何时具有足够依据独立物化。

这些问题应通过后续纵向切片、V&V 和实际维护结果逐步回答。
