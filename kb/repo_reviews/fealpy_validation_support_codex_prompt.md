# FEALPy | Prompt | 面向 proposal 软件验证支撑工作基础的 Repo Review Codex 任务提示词

- **版本**：v0.0
- **状态**：生效
- **入库位置**：`fealpy/kb/repo_reviews/fealpy_validation_support_codex_prompt.md`
- **启用条件**：当需要由 Codex 对 FEALPy GitHub 仓库执行一次面向 proposal“软件验证支撑工作基础”取证用途的结构化 Repo Review，并生成可入库 review 文档时，本提示词必须启用
- **适用范围**：`fealpy/` 仓库语境；`fealpy/kb/repo_reviews/suanhai_repo_review_skill.md` 已可读取调用的场景；围绕 FEALPy 作为基础算法支撑与原型验证平台的 review 协作任务

## 一、任务目标

请对 FEALPy GitHub 仓库执行一次面向 proposal“软件验证支撑工作基础”取证用途的 Goal-Driven Adaptive Repo Review。

本次 review 的目标不是做一般性的泛仓库点评，也不是做运行验证、性能验证或工程交付裁决，而是要在严格遵守 `fealpy/kb/repo_reviews/suanhai_repo_review_skill.md` 边界的前提下，系统评审 FEALPy 作为基础算法支撑与原型验证平台的组织基础，重点回答以下问题：

1. 当前仓库是否具备支撑复杂对象数值方法原型实现、比较与持续演化的结构基础。
2. 当前仓库是否具备支撑分层算例组织、测试与示例协同、验证入口组织的基础条件。
3. 当前仓库的 README、设计文档、实现目录、测试目录、示例目录与工具目录之间，是否已经形成可供研究协作持续复用的组织化支撑。
4. 当前仓库中哪些观察结果可作为 proposal 中“软件验证支撑工作基础”的一手材料。
5. 当前仓库中还存在哪些缺口，应被表述为后续补强方向，而不应被误写为已完成验证事实。

## 二、必须启用的本地 Skill 与上位约束

执行本任务时，必须显式读取并遵守：

1. `fealpy/kb/repo_reviews/suanhai_repo_review_skill.md`
2. 仓库本地存在的 `docs/repo_review/`
3. 仓库本地存在的 `docs/design/`
4. 仓库根目录 `README.md`

若本地 review 规范或本地模板对结构有更具体要求，优先服从 FEALPy 仓库本地约束；若不存在更具体约束，则采用本提示词中冻结的默认 review 骨架。

## 三、目标仓库与输出位置

### 3.1 目标仓库

目标仓库为 FEALPy GitHub 仓库：

`https://github.com/weihuayi/fealpy`

你可以直接访问该仓库并据此完成 review。

### 3.2 输出目录

本次 review 生成的新文档必须写入：

`fealpy/kb/repo_reviews/`

### 3.3 输出文件名

本次 review 的主题固定为：

`validation_support`

本次 review 的输出文件名固定为：

`fealpy_2026_03_16_validation_support_review.md`

### 3.4 归档要求

在生成新 review 文档前，必须检查：

- `fealpy/kb/repo_reviews/` 当前目录下已有的 review 实例文档
- `fealpy/kb/repo_reviews/history/` 中可比较的历史 review 文档

若当前目录中已存在旧的 review 实例文档，则先将其归档到：

`fealpy/kb/repo_reviews/history/`

归档时必须遵守以下纪律：

- 保持原有文件名
- 不得覆盖已有历史文件
- 不得移动技能文档、提示词文件、README、设计文档或其他非 review 实例文档
- `fealpy/kb/repo_reviews/suanhai_repo_review_skill.md` 不是 review 实例文档，不得归档
- 当前提示词文件不是 review 实例文档，不得归档

若无旧 review 可归档，应在最终 review 文档中显式说明。

## 四、扫描模式与仓库类型判断

### 4.1 扫描模式

由于当前任务给出了明确 review 目标，但未限定单一目录，因此本次任务必须采用：

Goal-Driven Adaptive Scan

### 4.2 仓库类型工作判断

在正式扫描前，必须先基于以下输入形成对 FEALPy 当前仓库类型的工作判断：

- `README.md`
- 仓库目录结构
- `docs/repo_review/`
- `docs/design/`

该工作判断可以是研究型、平台型、工具链型、应用型或混合型，但必须说明该判断只是本轮 review 的工作判断，而不是最终裁决。

### 4.3 review 目标判断

本轮 review 目标应主动收敛为以下复合目标：

- `full_repo`
- `design_consistency`
- `testing_and_examples`
- `build_and_ops`

其中：

- `full_repo` 用于形成整体结构认知与当前现状判断
- `design_consistency` 用于检查设计与实现的一致性
- `testing_and_examples` 用于检查测试、示例与验证组织条件
- `build_and_ops` 用于检查环境、构建、运维与可复现支撑条件

不得将本轮目标收窄为单纯代码风格检查，也不得扩写为运行验证任务。

## 五、必扫对象与自适应扩展要求

### 5.1 必须优先关注的对象

无论仓库最终结构如何，本次 review 都必须优先关注：

- `docs/repo_review/`
- `docs/design/`
- `README.md`
- `kb/repo_reviews/`
- `kb/repo_reviews/history/`
- 仓库根层目录结构
- `tests/`
- `examples/`
- `tools/`

### 5.2 自适应扩展要求

当默认重点目录不足以解释 FEALPy 作为基础算法支撑与原型验证平台的实现主线时，你可以自适应扩大扫描范围，但必须在最终 review 文档中显式说明扩展范围与扩展依据。

重点扩展时，应优先关注与以下主题直接相关的关键目录：

- backend
- mesh
- geometry
- discretization
- solver
- function space
- app
- tutorial
- benchmark
- 其他对理解原型承载能力、验证入口组织能力、模块替换能力有关键作用的目录

## 六、证据提取重点

本次 review 必须尽量提取以下类型的证据：

1. 目录职责与仓库主线之间的对应关系
2. README 对仓库角色、职责与入口的说明情况
3. 设计文档与实现目录之间的一致性线索
4. 测试目录、示例目录与原型验证组织之间的关系
5. `tools/` 中环境、构建、诊断、打包、平台适配等脚本的作用
6. 不同模块之间是否具备承载候选方法比较、替换与持续演化的组织基础
7. 当前仓库是否具备支撑局部算例、子结构算例或更复杂代表性算例逐步组织的前置条件
8. 当前仓库中哪些内容可支撑“软件验证支撑工作基础”的陈述，哪些只能作为后续补强方向

若某些内容未扫描、无法访问、证据不足或无法确认，必须显式说明不确定性，不得将推测写成事实。

## 七、判断纪律与禁止性行为

### 7.1 必须遵守的判断纪律

你必须始终遵守以下纪律：

- 不将未扫描内容写成已确认事实
- 不将静态扫描结果写成运行验证结论
- 不将改进建议写成裁决
- 不伪造上一轮比较
- 不删除不确定性说明
- 不删除未纳入范围说明
- 不跳过 `docs/repo_review/`
- 不跳过 `docs/design/`
- 不把 README 当作唯一事实来源
- 不扩大扫描范围却不在最终文档中说明

### 7.2 明确禁止的结论写法

本次 review 中，禁止出现以下表述方式：

- 已完成运行正确性验证
- 已证明算法正确
- 已证明性能达标
- 已满足 proposal 所需全部验证要求
- 已具备工业交付能力
- 已完成工程验证
- 已确认相关方法在目标对象上成立

### 7.3 允许采用的表述方式

本次 review 中，应优先采用以下表述方式：

- 从当前仓库静态结构看，已形成……
- 当前目录与文档组织显示出……
- 现有 `tests/`、`examples/` 与 `tools/` 初步表明……
- 当前仓库具备……的基础条件
- 当前仍缺少……
- 仅依据本轮静态扫描，尚不能判断……
- 当前观察更适合作为……的支撑线索，而不是最终验证结论

## 八、与 proposal 的对齐要求

请始终围绕以下 proposal 使用语境组织 review 结论：

1. FEALPy 在该 proposal 中被定位为基础算法支撑与原型验证平台。
2. proposal 关注的是方法研究、原型验证、反馈修正之间的组织化支撑。
3. proposal 需要的是“软件验证支撑工作基础”的一手材料，而不是工业级软件宣传文本。
4. review 结论应优先支撑以下方面的判断：
   - 复杂对象离散表达的组织承载基础
   - 候选方法比较与模块替换的组织条件
   - 分层算例组织与持续迭代验证的基础条件
   - 模块化、可复现、可扩展的研究软件支撑条件
5. 任何观察若无法直接支撑 proposal 表述，应明确归入问题、风险或后续补强方向，而不是勉强写成优势。

## 九、最终 review 文档的默认骨架

若 FEALPy 仓库本地 review 规范未提供更具体骨架，则本次 review 文档必须尽量采用以下结构：

# FEALPy Repo Review | 2026-03-16 | validation_support

## 1. Review 定位与本轮范围

说明本轮 review 的目标、定位、采用的扫描模式，以及本轮不纳入范围的内容。

## 2. 输入材料与扫描基线

说明已读取的入口材料、本地 review 规范、设计文档、README、关键目录以及本轮的扫描基线。

## 3. 与上一轮相比的变化摘要

若存在可比较的历史 review，则给出变化摘要；若不存在，则显式写明当前无可比较上一轮。

## 4. 当前现状

给出对 FEALPy 当前仓库角色、主要主线与当前结构状态的概括性判断。

## 5. 结构理解与一致性观察

围绕 README、设计文档、关键目录与当前实现，分析结构理解与一致性情况。

## 6. 面向原型验证平台的能力观察

重点分析以下方面：

- 原型承载能力
- 模块替换与候选方法比较能力
- `tests/` 与 `examples/` 的验证组织角色
- `tools/` 对环境、构建与复现的支撑
- 分层算例组织的前置条件
- 持续演化与多人协作的组织基础

## 7. 当前主要问题与风险

指出当前主要缺口、张力、断点与风险，但不得夸大为否决性结论。

## 8. 改进方向建议

提出面向后续补强的建议，且必须保持建议语气，不得写成裁决。

## 9. 面向 proposal 的可直接引用表述候选

本节必须单独存在，并至少拆成以下三组：

### 9.1 可用于“研究基础”的表述候选

提炼可支撑已有平台基础、已有算法组织基础、已有方法原型组织基础的表述。

### 9.2 可用于“工作条件”的表述候选

提炼可支撑软件平台、目录组织、测试与示例组织、环境与工具支撑条件的表述。

### 9.3 可用于“软件验证支撑工作基础”的表述候选

提炼最贴近当前 proposal 用途的表述，强调“验证支撑基础”而非“已完成验证”。

## 10. 后续动作建议

给出最小后续动作建议，例如：

- 文档入口补强
- 设计与实现映射补强
- `tests/` 与 `examples/` 关系补强
- benchmark 或代表性算例组织补强
- 构建与环境说明补强
- 历史 review 演化补强

## 十、执行结果要求

完成任务后，你只能进行以下两类修改：

1. 必要的旧 review 实例归档
2. 新建并写入 `fealpy/kb/repo_reviews/fealpy_2026_03_16_validation_support_review.md`

除上述两类动作外，不得修改其他无关文件。

若你发现仓库本地存在更具体的 review 规范、模板或目录纪律，应优先服从，并在最终 review 文档中说明你采用了哪些本地约束。

若因访问限制、仓库状态异常、目录缺失或证据不足导致部分任务无法完成，必须在最终 review 文档中显式说明，而不得静默跳过并假装完成。

## 十一、最终交付标准

只有在同时满足以下条件时，才可视为任务完成：

1. 已读取并遵守 `fealpy/kb/repo_reviews/suanhai_repo_review_skill.md`
2. 已优先检查 `docs/repo_review/`、`docs/design/` 与 `README.md`
3. 已形成仓库类型工作判断与 review 目标判断
4. 已说明扫描范围与扩展范围
5. 已完成旧 review 识别与必要归档
6. 已生成新的 review 文档并写入目标目录
7. 已显式说明未纳入范围与不确定性
8. 未将静态扫描写成运行验证结论
9. 已包含“面向 proposal 的可直接引用表述候选”专节
10. 未污染无关文件
