# FEALPy | Task Object Boundary | 新网格模块自动化测试系统三阶段任务对象边界

- **版本**：v0.2
- **状态**：草案
- **入库位置**：`kb/developments/new_mesh_module/mesh_02_test_system/mesh_02_test_system_object_boundary.md`
- **启用条件**：当需要界定“新网格模块自动化测试系统三阶段任务”的对象边界时，本文件必须启用
- **适用范围**：FEALPy 新网格模块自动化测试系统建设任务

本文档用于界定当前 Task 直接建设什么、不直接建设什么，以及与相邻对象如何分界。

## 一、边界定位

本 Task 的直接对象是新网格模块自动化测试系统的三阶段建设：调研、MVP、增量完善。

调研阶段只回答成熟项目如何组织自动化测试系统，以及哪些做法可迁移到 FEALPy 新网格模块；MVP 阶段只做最小可运行、可验证的测试系统；增量完善阶段只在既有 MVP 基础上补齐能力，不把任务扩展成完整覆盖率工程。

## 二、纳入范围

本 Task 纳入以下内容：

1. 调研约 3 个成熟项目的自动化测试系统组织方式。
2. 分析成熟项目中的测试层级划分方式，包括单元测试、集成测试、回归测试、慢测试或性能测试等。
3. 分析测试目录、测试文件命名、测试数据、fixture、conftest、参数化测试与共享断言逻辑的组织方式。
4. 分析测试可重复性相关实践，包括固定测试数据、随机种子、临时文件、浮点数比较和最小复现场景。
5. 分析 CI 中的测试触发、测试选择、矩阵配置、失败报告、覆盖率输出与本地复现方式。
6. 提炼 MVP 的最小测试对象、最小入口、最小验收标准和最小可复现信息要求。
7. 设计增量完善阶段的扩展方向，包括回归样例补齐、报告增强、数据管理优化和执行策略收敛。
8. 标注不适合当前任务直接照搬的实践，并说明原因。
9. 为后续测试用例生成、测试系统设计和最小测试矩阵梳理提供输入建议。

## 三、排除范围

本 Task 明确不包含以下内容：

1. 不直接编写新网格模块的正式测试文件。
2. 不直接建设完整的 FEALPy CI 配置。
3. 不直接设计覆盖所有场景的新网格模块测试系统架构。
4. 不追求新网格模块测试覆盖率最大化。
5. 不测试 FEALPy 其它模块。
6. 不为了调研覆盖面而扩展到与新网格模块无关的项目实践。
7. 不把调研文档写成 pytest、GitHub Actions 或 coverage 工具教程。
8. 不把 AI 生成的一次性脚本视为可入库测试资产。
9. 不在本阶段展开大规模 Bug 修复或问题单归档；若自然发现相关风险，只记录为后续输入。

## 四、相邻对象分界

与“新网格模块 API 与高风险接口梳理”的分界：

- 本 Task 可说明成熟项目如何识别测试对象和高风险接口。
- 具体梳理 FEALPy 新网格模块的公开 API、核心数据流和高风险接口，属于后续阶段。

与“测试用例生成”的分界：

- 本 Task 可提出哪些类型的测试适合优先自动化。
- 实际编写单元测试、集成测试、回归测试样例，属于后续阶段。

与“自动化测试系统设计”的分界：

- 本 Task 可提炼 CI 触发、报告输出、测试选择等可借鉴原则。
- 具体确定 FEALPy 的 workflow、命令入口、目录结构、marker 规范和覆盖率策略，属于后续阶段。

与“Bug 与设计问题上报”的分界：

- 本 Task 可指出成熟项目如何记录失败样例和最小复现信息。
- 针对新网格模块的实际 Bug 复现、归类和上报，属于后续测试实施阶段。

与“FEALPy 既有测试体系基线梳理”的分界：

- 本 Task 可在必要时把 FEALPy 当前测试组织作为背景参考。
- 对 FEALPy 现有测试目录、配置和运行结果的系统性基线梳理，若规模较大，应作为后续独立工作处理。

与“三阶段任务推进”的分界：

- 本 Task 可定义 MVP 应覆盖的最小闭环。
- 具体实现细节、目录落地、测试命令与 CI 脚本，属于 MVP 与增量完善阶段。
- 增量完善阶段只围绕已有 MVP 继续扩展，不重新推倒重来。

## 五、待确认边界点

- 是否需要在本 Task 中产出“最小测试矩阵草案”，还是仅提供生成该矩阵的原则输入。
- 调研项目是否必须全部来自科学计算或网格领域，还是允许加入一个通用 Python 项目作为工程化对照。
- MVP 是否必须先支持本地运行，再补 CI，还是应同步考虑最小 CI 入口。
