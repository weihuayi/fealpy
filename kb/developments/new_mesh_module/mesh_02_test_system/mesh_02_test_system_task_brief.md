# FEALPy | Task Brief | 新网格模块自动化测试系统三阶段任务

- **版本**：v0.2
- **状态**：草案
- **入库位置**：`kb/developments/new_mesh_module/mesh_02_test_system/mesh_02_test_system_task_brief.md`
- **启用条件**：当需要为“新网格模块自动化测试系统三阶段任务”建立稳定本体表达时，本文件必须启用
- **适用范围**：FEALPy 新网格模块自动化测试系统建设任务

本文档用于定义当前 Task 的稳定本体表达，回答该 Task 是什么、为什么成立、三个阶段分别要做什么，以及对象级完成判据为何。

## 一、Task 定位

本 Task 是新网格模块自动化测试系统建设任务，分为调研、MVP 和增量完善三个阶段。

第一阶段先调研成熟项目的测试系统实践，提炼可迁移原则；第二阶段搭建一个可运行、可验证的最小可用版本；第三阶段基于真实运行结果持续补齐测试组织、数据管理、报告输出和 CI 适配能力。

本 Task 的核心对象是“面向新网格模块的自动化测试系统建设”，不是单纯的工具学习，也不是一次性补齐全部测试覆盖。

## 二、核心问题与主目标

当前新网格模块处于重构与迭代过程中，需要一套可持续扩展、可回归、可复核的自动化测试机制。若直接进入实现，容易出现测试目录混乱、测试粒度不清、测试数据不可复现、CI 执行范围不稳定、失败信息难以定位等问题。

本 Task 需要先回答以下核心问题：

1. 成熟 Python 科学计算项目、网格相关项目或工程化较成熟的开源项目，通常如何组织自动化测试系统。
2. 如何基于调研结论确定新网格模块 MVP 阶段的最小测试范围、最小目录结构和最小运行入口。
3. 如何在增量完善阶段逐步加入单元测试、集成测试、回归测试、慢测试和失败报告机制。
4. 如何组织测试夹具、测试数据、参数化样例、随机种子、临时文件与失败报告。
5. 如何在 CI 中选择测试范围、输出结果、提供最小复现信息。
6. 哪些做法可以直接借鉴，哪些做法不适合当前任务照搬。

本 Task 的主目标是形成一条从调研到 MVP 再到持续完善的建设路径，并提炼出可直接进入后续设计阶段的原则性输入。

## 三、阶段输出预期

本 Task 的输入包括：

- 新网格模块自动化测试系统建设任务的总体说明。
- 当前任务阶段的调研范围、MVP 目标和增量完善目标。
- 约 3 个成熟项目的公开测试组织、CI 配置、贡献指南或开发文档。
- FEALPy 新网格模块后续测试系统建设的约束与目标。

本 Task 的输出包括：

- 成熟项目自动化测试系统调研记录。
- 新网格模块测试系统 MVP 方案，包含最小目录、最小入口、最小测试矩阵和最小验收标准。
- 增量完善路线，说明后续如何补齐测试分层、数据管理、失败报告和 CI 适配。
- 可迁移到 FEALPy 新网格模块的设计原则。
- 不适合当前任务直接照搬的实践及原因说明。
- 面向后续测试用例生成和自动化测试系统设计的输入建议。

## 四、对象级完成判据

本 Task 达到对象级完成，需要满足以下条件：

1. 已选取约 3 个成熟项目作为调研对象，并说明选择依据。
2. 已形成 MVP 的最小测试范围、最小入口和最小验收标准。
3. 已给出增量完善的阶段路线，能够说明后续如何从 MVP 逐步扩展到稳定可维护的系统。
4. 调研结论不是停留在“项目使用了什么工具”，而是明确说明“为什么适合借鉴、借鉴什么、哪些不适合 FEALPy 新网格模块照搬”。
5. 已提炼出可复用设计原则，能够作为后续新网格模块测试用例设计和测试系统设计的依据。
6. 文档内容可以被后续阶段直接引用，用于支撑最小测试矩阵、测试目录规范、测试数据组织与 CI 运行策略设计。

## 五、待确认点

- 最终选取的 3 个成熟项目是否固定为科学计算与网格相关项目，还是允许加入一个通用 Python 工程化项目作为对照。
- MVP 的最小范围是否只覆盖新网格模块核心链路，还是需要同时包含一小组回归样例。
- 是否需要把输出拆分为调研记录、MVP 说明和增量完善清单三个独立文档。
