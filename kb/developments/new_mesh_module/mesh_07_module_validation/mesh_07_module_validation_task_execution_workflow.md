# FEALPy | Task Execution Workflow | 新网格模块团队研究工作验证 任务执行工作流

- **版本**：v0.1
- **状态**：草案
- **入库位置**：`kb/developments/new_mesh_module/mesh_07_module_validation/mesh_07_module_validation_task_execution_workflow.md`
- **启用条件**：当当前 Task 需要稳定组织执行 How、节点、输入输出、V&V 执行接口、反馈回流与收口条件时，本文件必须启用
- **适用范围**：新网格模块合并 `develop` 后的团队并行研究工作验证、缺陷整理与结果汇总

本文档定义当前 Task 的执行工作流。执行采用“固定基线和登记 -> 成员并行验证 -> 问题复现与去重 -> 汇总复核 -> 回流和收口”的方式。

## 一、执行依据与 Workflow 定位

执行依据：

- `mesh_07_module_validation_task_requirement.md`
- `mesh_07_module_validation_task_brief.md`
- `mesh_07_module_validation_task_object_boundary.md`
- `mesh_07_module_validation_task_target_asset_design.md`
- `mesh_07_module_validation_task_verification_and_validation_design.md`

本 Workflow 只组织执行 How，不改变 V&V 对象、结果强度或父任务网络。执行负责人、验证窗口与复核人由模块负责人在启动时补充。

## 二、Workflow 输入与输出

### 2.1 输入

- 已合并新网格模块的 `develop` 完整提交哈希；
- 团队成员名单、验证负责人、复核人和验证时间窗；
- 每位成员的 FEALPy 研究工作适用性声明；
- 适用成员的代表性研究入口、环境、输入和预期依据；
- 本任务成员记录模板与缺陷台账。

### 2.2 输出

- 每位成员一份验证记录或不适用声明；
- 问题的最小复现与必要支撑材料；
- 去重、分类、分级和复核后的缺陷台账；
- 面向 mesh_05/06 回流和 mesh_08 的验证结果摘要。

## 三、Workflow Node

| 节点编号 | 节点名称 | 节点职责 | 输入 | 输出 | 进入条件 | 完成条件 |
|---|---|---|---|---|---|---|
| N-01 | 固定验证基线与责任 | 记录 commit、支持环境、时间窗、成员、汇总人和复核人 | 合并记录、成员名单 | 本轮验证头信息 | 新网格模块已合并 `develop` | 完整 commit 和责任主体已记录；工作区附加修改规则已说明 |
| N-02 | 成员适用性与用例登记 | 每位成员声明是否有 FEALPy 研究工作；适用者选择代表性用例 | N-01 输出、成员研究工作 | 用例登记或不适用声明 | N-01 完成 | 所有成员完成登记；用例有入口和预期依据 |
| N-03 | 成员并行研究验证 | 在统一基线上运行真实研究流程，记录环境、命令、结果、异常和限制 | 用例登记、成员记录模板 | 成员验证记录、原始问题报告 | N-02 完成 | 适用成员至少运行一个用例；不适用成员已说明原因；记录字段完整或注明缺失原因 |
| N-04 | 问题分诊与独立复现 | 为报告分配编号，去重，提取最小复现，区分模块 Bug、迁移遗漏、上层误用、文档或环境问题 | N-03 输出 | 缺陷复现材料、初步台账 | 至少出现一个问题时触发 | 每个问题有状态、类别、影响、复现结果和原记录回链 |
| N-05 | 汇总与人工复核 | 清点成员覆盖，复核缺陷分类和严重度，形成通过/失败/阻塞/未覆盖统计 | 全部成员记录、缺陷台账 | 经复核台账、结果摘要草稿 | N-03 完成；N-04 对已报问题完成 | 统计可回算；限制、冲突、未知和未验证范围已列出 |
| N-06 | 回流与收口准备 | 把确认问题路由到实现/测试/文档接口，提交 mesh_08 输入 | N-05 输出 | 回流清单、经复核结果摘要 | 模块负责人完成 N-05 复核 | 高风险项有处置责任；摘要可回链；mesh_08 进入建议已记录 |

## 四、Transition 与反馈回流

| 关系编号 | 来源节点 | 目标节点或回流对象 | 触发条件 | 处理方式 |
|---|---|---|---|---|
| T-01 | N-01 | N-02 | 基线和责任已固定 | 发布 commit、环境和记录位置，开始登记 |
| T-02 | N-02 | N-03 | 全员完成适用性登记 | 适用成员并行执行，不适用成员等待汇总核对 |
| T-03 | N-03 | N-04 | 发现异常、错误结果、性能阻塞或文档歧义 | 先保留原记录，再提取最小复现和去重 |
| T-04 | N-04 | N-03 | 问题可能由研究脚本、输入或环境导致 | 由原成员补充或重跑，更新记录但不删除历史观察 |
| T-05 | N-03/N-04 | N-05 | 验证窗口结束且记录收齐 | 汇总覆盖与缺陷状态，人工复核 |
| T-06 | N-05 | mesh_05/专项修复 | 确认可复现的算法、迁移或实现问题 | 创建承接项，附最小复现和影响范围 |
| T-07 | N-05 | mesh_06 | 确认 Bug 需要回归保护或暴露覆盖缺口 | 提交回归测试候选与断言依据 |
| T-08 | N-05 | 文档/上层维护者 | 问题属于语义歧义、上层误用或适配缺失 | 路由到相应责任接口并保留分类依据 |
| T-09 | N-05 | N-01/N-03 | 验证期间基线发生高影响变化 | 冻结旧轮次并明确受影响成员重跑范围 |
| T-10 | N-06 | mesh_08 | 结果摘要已复核且重大问题有处置状态 | 提供验收输入，不预先给出最终结论 |

## 五、V&V 执行接口与收口条件

| V&V 接口 | 承接来源 | 执行节点 | 输出对象 | 使用边界 |
|---|---|---|---|---|
| 研究场景适用性确认 | VV-T-01 | N-02, N-03 | 成员验证记录 | 只覆盖实际用例、环境和规模 |
| 异常复现与符合性验证 | VV-T-02 | N-04 | 缺陷复现材料和台账项 | 未独立复现项保持候选或未知状态 |
| 团队验证结果综合 | VV-T-03 | N-05, N-06 | 缺陷台账与结果摘要 | 不替代最终验收、发布或能力结论 |

本 Workflow 进入收口准备必须同时满足：

1. 基线提交和验证环境已记录；
2. 每位成员均提交验证记录或不适用声明；
3. 每个适用成员至少完成一个代表性用例，或明确记录无法执行的阻塞；
4. 所有观察问题已进入台账并回链原始记录；
5. 可行动问题具有独立复现结果或复现阻塞说明；
6. 台账和摘要已由人工复核；
7. 重大问题有负责人、后续接口或明确的待裁决状态；
8. 未验证范围和结果限制没有被省略。

## 六、成员执行最小操作规范

### 6.1 开始前

1. 获取任务负责人指定的 `develop` 提交，不自行用更新后的分支覆盖本轮基线。
2. 创建隔离环境或记录现有环境；不得在记录中泄露凭据。
3. 复制成员记录模板到 `records/<member_slug>_validation_record.md`。
4. 若无基于 FEALPy 的研究工作，填写不适用原因后提交记录，不另造用例。

### 6.2 执行中

1. 运行可代表日常研究路径的最小端到端用例，而非只执行 import。
2. 记录准确命令、关键配置、输入生成方式和预期依据。
3. 对数值结果使用解析解、已知不变量、收敛趋势或经成员确认的参考结果判断。
4. 任何异常均先保存原始事实；需要修改研究脚本才能继续时，记录修改内容和原因。
5. 不把大数据、密钥、受限代码或无关完整日志提交到任务目录。

### 6.3 发现问题时

1. 在成员记录的问题表中增加一行，分配临时报告编号 `R-<member_slug>-NN`。
2. 保留异常类型、完整 traceback 的关键部分、预期与实际差异、首次失败命令和环境。
3. 尝试缩小网格、输入和调用链，但不以破坏失败条件为代价。
4. 由汇总人分配唯一缺陷编号 `M07-###`，合并重复报告并保留所有来源回链。
5. 重大静默错误、数据损坏或广泛阻塞立即升级，不等待验证窗口结束。
