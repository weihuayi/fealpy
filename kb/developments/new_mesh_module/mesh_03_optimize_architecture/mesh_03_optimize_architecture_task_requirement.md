本文档用于界定当前 Task 所要满足的真实问题、真实需求、约束条件与成功条件。

## 一、背景与核心问题

新网格模块在 `mesh_01_validation` 验证阶段被证明在整体架构上是可行的，但在实际使用中暴露了8个接口层面的不足，直接影响了算法开发效率与代码可读性。本任务需要通过设计与实现这8项优化，使模块更符合真实网格算法的需求，从而为后续大规模使用提供稳定基础。

## 二、已确认需求

### 反向邻接查询
- 用户能通过公开 API 快速获得 `edge → tri` 或 `tri → tri` 的邻接关系。
- 接口应支持遍历相邻实体，并清晰说明维数与关系方向。
- 实现方式可以是反向 relation 推断，或专用的 `cell_to_cell_neighbors()` 接口。

### 几何量接口的二/三维自适应
- `TriangleSchema.measure()` 应能正确处理二维坐标（行列式面积）与三维坐标（叉乘范数）。
- `TriangleSchema.normal()` 应明确在二维场景下的返回语义（标量有向法向、二维旋转法向或不提供）。
- `TetrahedronSchema.measure()` 应对三维体积有无异常。
- 接口实现应包含维数检查，异常情况应给出清晰错误提示。

### opposite-vertex 元数据与局部顺序规范
- 所有 simplex schema（triangle, tetrahedron, line）应明确 `local_faces` 的语义。
- 对于 simplex，应记录"第 i 条边/面与顶点 j 的对偶关系"（即 opposite-vertex 映射）。
- 元数据可存储为 schema 属性或文档说明，但必须可在代码中被查询到。
- 语序约定应与常见几何/网格文献对齐，或明确标注当前采用的约定。

### 边界缓存管理优化
- `MeshBlock` 或 `BoundaryInferencer` 应实现缓存失效机制。
- 在 `add_sector()`、relation 写入、indices 修改等关键路径上自动清空 `_cache_boundary_info`。
- 或提供显式的 `invalidate_boundary_cache()` 接口供用户手动触发。
- 文档中应清晰说明缓存生命周期与失效条件。

### EntitySchema 接口管理完善
- `EntitySchema` 应明确区分"已实现"与"预留"接口。
- 已实现接口应能稳定被调用；预留接口应标记为 `NotImplementedError` 或 `TODO`。
- `EntityView` 在调用可能未实现的接口前，应检查能力并给出有意义的错误信息（如"当前 schema 不支持该操作"）。
- 文档中应列出各 schema 的能力清单（支持哪些操作，不支持哪些）。

### 统一文档与代码术语
- 设计文档应更新为与代码实现一致的术语（如 MeshBlock 而非 MeshStorage）。
- 或提供清晰的术语映射表，说明设计文档术语与代码术语的对应关系。
- 新增的类、属性、方法应在代码注释与文档中保持术语一致。

### 支持形状 + 维数双重实体选取机制
- 用户应能同时按实体形状名称与拓扑维数来查询实体。
- 例如：`mesh.entity("triangle", 2)` 或 `mesh.entity(shape="triangle", dimension=2)`。
- 或提供专用接口如 `mesh.sector_by_shape_and_dim("triangle", 2)`。
- 接口应能正确处理维数不匹配的情况（如询问"维数0的triangle"应返回空或错误提示）。

### view 中支持便利查询 API
- `EntityView` 或 `Mesh` 应提供常用的邻接查询接口，如：
  - `cell_to_cell_neighbors(cell_type)` - 获取某类单元的邻接关系。
  - `on_boundary(entity_type)` - 获取某类实体中的边界实体。
  - `gradient_indices(entity_type)` - 获取计算梯度所需的实体指标关系。
- 这些接口应基于现有 relation 与 boundary 信息组合，不引入新的底层数据存储。
- 接口应清晰说明返回值的形状、含义与性能特征。

## 三、约束条件

- 优化过程不应破坏现有的核心分层设计（schema / storage / view / topology）。
- 向后兼容性应保持：现有 `mesh_01_validation` 算例不需大幅改写（API 迁移除外）。
- 不引入新的外部依赖；如需额外性能优化，应在现有技术栈范围内实现。
- 新增代码应遵循当前项目的风格与命名约定。
- 文档更新应清晰标注变更点，便于用户理解迁移路径。

## 四、成功条件

满足以下条件即视为需求被满足：

- **反向邻接**：用户能通过公开接口在算例中直接查询邻接关系，无需手写派生逻辑。
- **几何适应**：二维与三维网格都能无异常地调用几何量接口，并得到正确结果。
- **元数据清晰**：代码中能找到每个 simplex schema 的 opposite-vertex 映射或方向约定。
- **缓存一致**：拓扑修改后重新查询边界，结果与拓扑变化同步更新。
- **接口清晰**：调用未实现接口时，错误信息能清楚指出问题原因。
- **术语一致**：从设计文档跳转到代码，术语能对得上；或映射表清晰可用。
- **双重查询**：用户能便捷地按形状+维数组合查询实体。
- **便利 API**：常见的邻接、边界、梯度查询能一行代码完成，无需用户自己实现。
- **验证充分**：新增/修改的功能都有对应测试或验证脚本，并通过测试。

## 五、待确认需求

- 反向关系推断的完整边界：是否需要支持任意维数间的推断，还是只支持相邻维数？
- 二维 `normal()` 的返回语义：是否需要返回标量有向法向，还是其他约定？
- 缓存失效的粒度与触发条件：是全量失效还是支持细粒度失效？
- 便利 API 的完整范围：是否需要包含更复杂的查询如"某个边界上的所有单元"？
- 对性能的约束：是否允许为便利 API 计算临时辅助结构，还是必须直接基于现有数据？
