本文档用于界定当前 Task 所要满足的真实问题、真实需求、约束条件与成功条件。

## 一、背景与核心问题

新网格模块已经完成接口与架构优化，但算法实现仍分散在旧网格模块、view 层或临时脚本中，导致算法入口不统一、难以复用、难以验证。当前任务需要把算法实现迁移并收敛到 Entity Schema，使算法成为“规则模板层的稳定能力”，而不是上层调用者的临时拼装。

## 二、已确认需求

### 1. 算法迁移范围与优先级

- 迁移范围以 **Entity Schema 可承载的算法** 为准，包括：
  - 几何类算法：`measure`、`barycenter`、`grad_lambda`、`normal`、`tangent` 等。
  - 多重指标类算法：暂定只迁移 `multi_index`，以 `fealpy/mesh/topology/ipoints.py` 中的单纯形多重指标生成器为基础。
  - 基于实体规则的拓扑/局部索引算法：`local_entity` 等。
- 迁移必须覆盖 **优先级最高的核心算法**，并为其它算法留出可扩展接口。

### 2. 接口标准对齐

- 迁移后的算法必须严格对齐 Entity Schema 接口标准（见 mesh_03 资产）。
- 方法签名与返回类型必须与 `EntitySchema` 定义一致，不新增非标准参数。
- 返回值形状与语义必须与接口文档一致，避免下游误用。

### 3. 行为一致与差异说明

- 迁移后的算法应与旧实现结果一致；如需调整，应在迁移记录中明确差异与原因。
- 对二维/三维差异处理需要明确说明，避免隐式行为。

### 4. `ccw` 元数据补充

- 每种 schema 增加 `ccw` 类属性，表达子实体的逆时针排列顺序。
- `ccw` 的内容允许与 `local_faces` 不同，需显式记录并可被查阅。

### 5. 迁移映射与可追溯性

- 必须形成“旧实现 → 新 Schema 方法”的映射表。
- 每个迁移项需标注来源、替代位置、验证方式与负责人。

### 6. 最小验证资产

- 每类算法至少提供一种可复现验证方式（单元测试或脚本）。
- 验证结果需能回链到具体 schema 与具体算法方法。

## 三、约束条件

- **只向 Entity Schema 迁移算法**，不扩展到 view / storage / topology 层的改造。
- 不引入新的外部依赖，不引入与算法迁移无关的大规模重构。
- 迁移过程中新增算法必须可追溯来源，不鼓励无依据的“顺手新增”。
- 迁移后的接口必须保持稳定，不在本任务中提出新的 API 设计。
- `normal()` 与 `tangent()` 必须返回 Tensor，形状为 `[实体数, 方向数, 几何维数]`，允许方向数为 0。

## 四、成功条件

满足以下条件即视为需求被满足：

- 优先级算法全部迁移到 Entity Schema，且接口标准一致。
- 迁移映射表完整、可追溯、可复查。
- 迁移算法有可复现验证证据。
- `ccw` 属性在所有 schema 中可查询且含义明确。
- 下游调用方无需绕过 schema 才能使用算法。
- 任务输出不越界到架构重构、测试系统建设或上层模块改造。

## 五、待确认需求

- 迁移优先级清单的最终版本（哪些算法必须在本阶段完成）。
- `normal()` 与 `tangent()` 在不同维度与嵌入维度下的统一返回语义。
- `ccw` 在非单纯形实体上的具体约定（如 quad/hex 的顺序规则）。
- 旧实现中不符合标准接口的算法是否需要拆分、重写或暂留待后续任务处理。
